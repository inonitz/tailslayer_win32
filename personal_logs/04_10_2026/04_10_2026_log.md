### I tried to find alternatives to VirtualAlloc2(), since calling it with the MEM_EXTENDED_PARAMTER just didn't fucking work what-so-ever:  

 ```sh
    constexpr uint64_t desiredSize = 1073741824; (Literally 1GiB)
    MEM_EXTENDED_PARAMETER extended {};
    memset(&extended, 0x00, sizeof(MEM_EXTENDED_PARAMETER));
    extended.Type = MemExtendedParameterAttributeFlags;
    extended.ULong64 = MEM_EXTENDED_PARAMETER_NONPAGED_HUGE;

    PVOID out = VirtualAlloc2(GetCurrentProcess (), NULL, 
        desiredSize,
        MEM_LARGE_PAGES | MEM_RESERVE | MEM_COMMIT,
        PAGE_READWRITE, 
        &extended, 
        1
    );
```

#### **^----------- THIS DOESNT WORK, NEVER!**

If you read the following resources, you can confidently come to the conclusion that your memory will be contiguous in physical memory, **IF** you manage to actually allocate with ```NONPAGED_HUGE```:

* [VirtualAlloc2](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualalloc2)
* [Large Page Support](https://learn.microsoft.com/en-us/windows/win32/memory/large-page-support)
* [MEM_EXTENDED_PARAMETER_NONPAGED_HUGE](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-mem_extended_parameter)
* [Stackoverflow Post Mentioning All this crap](https://stackoverflow.com/a/71543569)

Ofcourse, I haven't even Mentioned that the Large Page Support is for the minimum of 2MiB Pages! Not Necessarily Huge 1GiB Pages.  
There is literally little-to-no documentation on this abhorrent feature.  
The closest thing I could find is that I get better guarantees from allocating inside an unsigned Kernel driver, which is diabolical.  
In practice, you also still have to set the ```SeLockMemoryPrivilege``` User Token s.t you can properly allocate memory using the ```MEM_LARGE_PAGES``` Flag  
In The end, I had to settle (for now) with ```VirtualAlloc``` and the ```MEM_LARGE_PAGES``` Flag, in hopes that given that I asked for a whole 1GiB, it maybe be contiguous in the physical memory mapping. This is the final allocation func for now:  

```sh
    inline void* allocateHugePages(size_t desiredSize) 
    {
        size_t largepageSize = GetLargePageMinimum();
        if (desiredSize % largepageSize != 0) {
            // Round up to nearest multiple
            desiredSize = (desiredSize + largepageSize - 1) & ~(largepageSize - 1);
        }
        // Make sure there is privilege to lock the physical memory s.t it wont be swapped to disk
        if(!SetLockMemoryPrivilege(true)) {
            PrintLastError("Could not acquire SeLockMemoryPrivilege. Large pages will fail\n");
            return nullptr;
        }
        PrintLastError(""); // Making sure nothing bad happend before the allocation
        PVOID out = VirtualAlloc(
            NULL, 
            desiredSize, 
            MEM_RESERVE | MEM_COMMIT | MEM_LARGE_PAGES, 
            PAGE_READWRITE
        );

        if(out == nullptr) {
            PrintLastError("allocateHugePages (VirtualAlloc2) Failed\n");
        }
        return out;
    }
```

#### **The conclusion is that upon further inspection, it seems that the 1GiB Allocation that must be done on LaurieWireds' Code May not necessarily be satisfied, and must be manually verified.**

And oh boy, good luck getting your driver signed by a trusted authority!  
  
The main point was to gain access to Physical Memory Pointers, i.e Converting Virtual -> Physical Addresses.  
This is mostly relevant for the HardwareUtils::virt_to_phys function,  
running in the benchmark executable  
My main gripe, is that on linux you can just read the pagemap with ```open("/proc/self/pagemap", O_RDONLY)``` and a little bit of ```sudo ./foobar```,

* Administrator Privileges
* A Kernel Driver To Convert the addresses
